# NexusTasks — техническая спецификация

Документ фиксирует технические решения проекта, на которые мы опираемся. Обновляется по мере принятия новых решений.

## 1. О проекте

**NexusTasks** — веб-приложение для управления задачами (SPA) со встроенным мессенджером. Регистрация идёт от лица компании (`RegistrationCompanyForm`), то есть предполагается мультипользовательская модель с компаниями/организациями.

Ключевые модули:

- **Задачи** — основной функционал управления задачами.
- **Мессенджер** — общение внутри приложения (чаты между сотрудниками компании). Подробности в разделе 6.

Текущее состояние:

- Активна только frontend-часть (`frontend/`).
- Backend отсутствует.
- Тестов нет, ESLint не настроен (только Prettier).

## 2. Стек

### Frontend (принято)

| Область | Технология |
|---|---|
| Фреймворк | Vue 3.5 (Composition API, `<script setup>`) |
| Язык | TypeScript ~5.8 |
| Сборка | Vite 7 |
| UI-библиотека | Nuxt UI v4 (`@nuxt/ui`, Tailwind CSS + Reka/Radix) — основной источник компонентов |
| Состояние | Pinia 3 |
| Роутинг | Vue Router 4 |
| Стили | Tailwind (через Nuxt UI) + SCSS (`sass`) для кастомных стилей |
| Форматирование | Prettier 3.6 |
| Проверка типов | `vue-tsc` |
| Node | `^20.19.0 \|\| >=22.12.0` |

Шрифты: Inter (основной), JetBrains Mono (моноширинный) — локально из `src/app/assets/fonts/`.

### Backend (не определён)

Стек будет выбран, когда дойдёт до бэкенда. До этого момента:

- Не закладывать в frontend жёсткую привязку к конкретному бэкенду.
- Обращения к API изолировать в отдельном слое (`shared/api`), чтобы замена бэка не затрагивала UI.
- Контракт API (эндпоинты, DTO, коды ошибок) описывать отдельно, когда бэк будет выбран.
- Мессенджеру потребуется real-time канал (WebSocket/SSE или аналог) — это влияет на выбор бэкенда.

## 3. Архитектура frontend

Feature-based слоистая структура (в духе Feature-Sliced Design). Исходники в `frontend/src/`:

```
src/
├── app/        # Точка входа: App.vue, router, глобальные стили и ассеты
├── pages/      # Страницы уровня роута (тонкие обёртки)
├── widgets/    # Составные UI-блоки, используемые страницами
├── features/   # Бизнес-логика: формы, действия пользователя
├── layouts/    # Обёртки-лейауты (DefaultLayout, AuthLayout)
├── stores/     # Pinia-хранилища
└── shared/     # api/, config/ (ROUTES), ui/ (PasswordInput), types/
```

Правила:

- В каждой папке `pages/`, `widgets/`, `features/` — свой срез с barrel-экспортом `index.ts`; компоненты лежат в подпапке `ui/`.
- Зависимости идут только вниз по слоям: `pages → widgets → features → shared`. Обратные и горизонтальные импорты между срезами одного слоя не допускаются.
- Алиас `@` → `./src`.
- Страницы содержат минимум логики, только компонуют виджеты.

### Лейауты

`App.vue` выбирает обёртку по `route.meta.layout`:

- `default` — шапка, боковая навигация, аватар-меню, переключатель цветовой темы.
- `auth` — минимальная обёртка (`<slot>`).

### Роутинг

Определён в `src/app/router/index.ts`:

| Путь | Страница | Лейаут |
|---|---|---|
| `/` | HomePage | default |
| `/registration` | RegistrationPage | auth |
| `/login` | LoginPage | auth |

Маршруты мессенджера (например, `/messenger`, `/messenger/:chatId`) будут добавлены при реализации.

### Конфигурация Nuxt UI (`vite.config.ts`)

- `primary`: `black`, `secondary`: `sky`, `neutral`: `neutral`.
- Контейнер: max-width `1920px`.

### Стили

- Точка входа: `src/app/assets/styles/main.css` (Tailwind + Nuxt UI).
- SCSS-партиалы: `_base.scss`, `_fonts.scss`, `_reset.scss`, `index.scss`.
- CSS-переменные (шкала отступов и т.д.): `variables.css`.

## 4. Команды

Все команды запускаются из `frontend/`:

```bash
npm run dev         # dev-сервер Vite
npm run build       # type-check + сборка
npm run build-only  # сборка без type-check
npm run preview     # предпросмотр production-сборки
npm run type-check  # vue-tsc
npm run format      # Prettier по src/
```

## 5. Планы на будущее: микрофронтенды

> Это **будущая** цель, сейчас не реализуется. Важно не принимать решения, которые сделают переход невозможным или дорогим.

Планируется внедрить архитектуру микрофронтендов. Конкретный подход (Module Federation, single-spa, iframe, Web Components и т.д.) **не выбран** — решим, когда придёт время. Мессенджер и задачи — естественные кандидаты на отдельные микрофронты.

Что учитывать уже сейчас:

- **Границы срезов.** Держать `features/` и `widgets/` независимыми друг от друга, общее выносить в `shared/`. Это упростит будущую нарезку на отдельные приложения.
- **Слабая связность.** Не завязывать срезы на глобальные сторы друг друга; межсрезовое взаимодействие — через явные интерфейсы, события или props.
- **Shared-слой.** Всё, что потенциально нужно нескольким микрофронтам (UI-кит, API-клиент, типы, авторизация), должно жить в `shared/` и быть кандидатом на вынос в отдельный пакет.
- **Состояние и авторизация.** Не размазывать логику сессии/токенов по проекту — сконцентрировать в одном месте, чтобы её можно было расшарить между микрофронтами.
- **Роутинг.** Не делать жёстких допущений о том, что приложение владеет всем URL; пути страниц собирать централизованно.
- **Стили.** Избегать глобальных стилей и селекторов, которые могут конфликтовать при совместной работе нескольких приложений на одной странице; отдавать предпочтение Tailwind-классам/scoped-стилям.
- **Версии зависимостей.** Vue, Nuxt UI, Pinia и Vue Router — потенциальные shared-зависимости; их версии нужно будет синхронизировать между микрофронтами.
- **Возможный переход на монорепозиторий** (npm/pnpm workspaces) — вероятно потребуется вместе с микрофронтами.

## 6. Мессенджер

Встроенный мессенджер — часть приложения (детальные требования будут уточняться).

Предварительные соображения:

- **Real-time.** Доставка сообщений в реальном времени (WebSocket/SSE — выбор зависит от backend). Транспорт изолировать в `shared/` (клиент соединения), UI от него не зависит.
- **Структура на frontend.** Отдельные срезы, например: `pages/messenger`, `widgets/chatList`, `widgets/chatWindow`, `features/sendMessage`. Не смешивать с логикой задач.
- **Состояние.** Отдельный Pinia-стор (чаты, сообщения, статусы прочтения, онлайн-статус); соединение и подписки — вне компонентов.
- **Связь с задачами.** Возможны ссылки на задачи из чатов и уведомления о событиях по задачам — реализовывать через явные интерфейсы, без прямых импортов между срезами.
- **Изоляция.** Мессенджер проектировать как самодостаточный модуль с минимальными внешними зависимостями (текущий пользователь, компания, тема) — это подготовка к выносу в микрофронт.
- **Открытые вопросы:** типы чатов (личные/групповые/по задачам), вложения, история и пагинация, уведомления, поиск.
